数据与算法的专业语言

埋点、漏斗、指标体系、A/B 测试、特征工程、模型上线……数据分析师和算法工程师用数据驱动决策。读懂这些词，你就能理解"数据说了什么"。

2026-06-05 阅读约 13 分钟 数据分析 · 算法工程 · 增长 建议先读第一、三篇

数据分析师（DA）和算法工程师（AE）在很多公司坐在同一个部门，但他们的工作性质不同：数分关注"发生了什么、为什么"，算法关注"怎么用模型自动做决策"。这两个角色共享一套底层语言，但在某些术语上各有侧重。

这篇按数据的生命周期来组织：数据从哪来 → 怎么分析 → 怎么做实验验证 → 算法怎么把数据变成模型。

本篇主题色为深紫，代表数据与算法角色。这两个角色是产品决策的"裁判"——他们用数据告诉所有人，一个功能到底有没有用。

第一层

数据从哪来——采集与基础设施

所有的数据分析都从数据采集开始。没有干净、完整的数据，所有分析都是空谈。这一层的词，是数据工作的地基。

数据采集相关术语
埋点 Event Tracking

在代码里插入的"传感器"——当用户做了某个动作（点击按钮、停留超过 3 秒、完成签到），就记录下来：是谁、在哪里、什么时间、做了什么。所有数据分析的原材料。

「签到按钮要埋点，记录 user_id、时间戳和当前页面，否则后面没法分析为什么签到率低。」

数据仓库 Data Warehouse

集中存储从各个系统（App、后端、第三方平台）汇聚过来的历史数据，专门为分析查询优化，而不是为实时业务操作服务。常见工具有 Hive、BigQuery、Snowflake。

「签到数据已经同步到数据仓库了，你直接查 dw.checkin_records 这张表。」

ETL Extract, Transform, Load

把数据从各处抽取（Extract）、清洗转换（Transform）、加载到数据仓库（Load）的自动化流程。是数据从"原始"变成"可分析"的必经之路。

「ETL 任务每天凌晨跑一次，把昨天的签到数据处理好放进仓库，早上来就能查到。」

数据质量 Data Quality

数据的准确性、完整性、一致性和及时性。"数据质量差"意味着可能有缺失值、重复记录或错误数值，会导致分析结论失真。

「这个签到数据有问题，有 5% 的记录 user_id 是空的，数据质量要先处理一下。」

维度 / 指标 Dimension / Metric

维度是分析的"角度"（按渠道、按城市、按用户年龄分），指标是被衡量的"数值"（签到人数、签到率、积分发放量）。"按城市看签到率"中，城市是维度，签到率是指标。

「按设备维度拆一下签到指标，看 iOS 和 Android 有没有差异。」

数据从产生到分析的完整链路

① 用户行为

第二层

数据分析——发生了什么

数据采集完毕，数据分析师的工作是把原始数字变成可以指导决策的结论。这一层的词，是他们在日常工作和汇报中最常用的。

数据分析相关术语
指标体系 Metric Framework

把产品目标分解成层次清晰的指标树——北极星指标在顶层，下面是支撑它的二级指标、三级指标，每一层都能解释上一层的变化原因。

「签到功能的指标体系：北极星是 D7 留存 → 二级是签到完成率 → 三级是按钮点击率和页面加载速度。」

同期群分析 Cohort Analysis

把在同一时间段注册或开始使用的用户归为一组，追踪这组人在后续时间里的行为变化。用来观察留存衰减曲线，找到"用户在哪个时间点开始流失"。

「做一个同期群分析，看签到功能上线前后注册的用户，30 天留存有没有差异。」

漏斗分析 Funnel Analysis

把用户完成某个目标的路径拆成多步，分析每步的转化率和流失率，找到最值得优化的断点。第三篇产品经理的"转化漏斗"讲的是同一个概念。

「漏斗分析显示从首页进入签到页的转化只有 40%，这一步流失太多了。」

用户分层 User Segmentation

按照行为特征、活跃程度、价值贡献把用户分成不同的群体，对每个群体采取不同的运营策略。比如把用户分成"高活跃""低活跃""沉睡"三层。

「先做用户分层，针对签到连续 7 天的用户推专属积分翻倍活动，而不是全量推。」

归因分析 Attribution Analysis

把一个结果（用户付费、用户流失）的功劳或责任分配给导致它的各个原因。比如用户付费，是因为签到积分、还是推送消息、还是价格促销？

「留存提升了 3%，归因分析后确认 70% 来自签到功能，30% 来自推送优化。」

数据分析师的日常产出通常是一张数据看板，让业务方和产品经理一眼看清核心指标的变化：

第三层

A/B 实验——用数据做决策

"感觉这个方案更好"和"数据证明这个方案更好"是两回事。A/B 实验是互联网公司最重要的决策工具，用来在不确定中找到确定的答案。

A/B 实验相关术语
对照组 / 实验组 Control / Treatment Group

对照组（A 组）接受现有方案，实验组（B 组）接受新方案，两组用户随机分配，其他条件相同，只有这一个变量不同。

「对照组看旧的签到按钮，实验组看新的红色按钮，对比签到完成率。」

显著性 Statistical Significance

判断实验结果是真实的差异还是随机波动的统计指标。通常要求 p-value < 0.05，即"这个差异有 95% 的概率不是偶然的"，才算有效结论。

「B 组签到率高了 2%，但还没有达到显著性，样本量不够，再跑一周。」

辛普森悖论 Simpson's Paradox

整体数据显示 A 更好，但分维度看每个子群体都是 B 更好的反直觉现象。数据分析时不拆维度分析，很容易得出错误结论。

「全量看 A 组更好，但辛普森悖论——分 iOS 和 Android 看，其实 B 组都更好。」

实验污染 Experiment Contamination

实验组和对照组的用户之间相互影响，导致实验结论失效。比如实验组用户把新功能告诉了对照组用户，对照组的行为也改变了。

「签到活动如果按设备分组，同一个人的两台设备分到不同组，会造成实验污染，要按用户 ID 分。」

第四层

算法工程——让机器自动做决策

数据分析师用数据回答"发生了什么"，算法工程师则用机器学习模型让系统自动做决策——比如"给这个用户推什么"、"这条评论是不是垃圾信息"。这是数据语言里最接近 AI 的那一层。

算法工程相关术语
特征工程 Feature Engineering

把原始数据转化成机器学习模型能理解的"特征"的过程。比如"用户最近 7 天的签到次数"就是一个特征，它比原始日志更直接地表达了用户的活跃程度。

「特征工程里加一个"连续签到天数"特征，用来预测用户明天是否还会签到。」

训练集 / 测试集 Training / Test Set

把历史数据分成两部分：训练集用来让模型"学习"规律，测试集用来验证模型在没见过的数据上表现如何。如果只用训练集评估，模型可能过拟合——在已知数据上很准，对新数据一塌糊涂。

「用 80% 数据做训练集，剩 20% 做测试集，别把测试集数据混进训练里。」

过拟合 Overfitting

模型把训练数据里的噪音和细节也"记住"了，导致在新数据上表现很差。就像死记答案不理解原理，一换题目就不会了。

「训练集准确率 97%，测试集只有 63%，明显过拟合了，需要加正则化。」

模型上线 / 上线推理 Model Deployment / Inference

把训练好的模型部署到线上系统，实时对新来的数据做预测。"推理"指的是模型接收输入、计算并输出结果的过程，是模型在生产环境工作的状态。

「模型训练完了，上线推理服务，让签到页面实时调用，预测用户今天是否会签到。」

召回率 / 精确率 Recall / Precision

评估分类模型的两个核心指标：精确率是"模型说是的里面真正是的比例"，召回率是"真正是的里面模型找出来了多少"。两者通常是此消彼长的关系。

「召回率太低了，很多要流失的用户我们没预测出来，拉低了拦截效果。」

推荐系统 Recommendation System

根据用户的历史行为和偏好，自动预测并展示用户可能感兴趣内容的算法系统。签到积分兑换页面的"猜你喜欢"就是推荐系统的典型应用。

「积分商城接入推荐系统，根据用户历史兑换记录个性化排序，兑换率预计提升 15%。」

容易混淆的地方

数分 vs 算法——一张图说清楚

很多人分不清数据分析师和算法工程师的区别，因为他们经常坐在一起，用的工具也有重叠。但他们解决的核心问题完全不同：

数据分析师 vs 算法工程师
📊数据分析师（DA）
核心问题：发生了什么？为什么？
核心工具：SQL、Excel、Tableau、Python
典型产出：数据报告、指标看板、A/B 实验结论
日常对话："签到率下跌了，原因在这里"
服务对象：产品、运营、业务决策者
🤖算法工程师（AE）
核心问题：如何让机器自动做决策？
核心工具：Python、TensorFlow、PyTorch、Spark
典型产出：推荐模型、风控模型、用户流失预测模型
日常对话："这个模型的召回率还能优化"
服务对象：产品系统、线上服务（实时调用）

简单类比：数分是"侦探"，看现场找线索得出结论；算法工程师是"自动驾驶系统"，训练完直接在线上跑，不需要人每次手动判断。
