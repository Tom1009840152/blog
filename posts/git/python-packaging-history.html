Python 生态

Python 包管理工具简史：
从 distutils 到 uv

二十多年里，Python 社区为了"怎么装一个包"这件小事，先后造出了十几种工具。这篇文章按时间线捋一遍它们各自解决了什么问题、又留下了什么坑，帮你理解今天这套 pyproject.toml 体系是怎么来的。

2026-07-07 阅读约 9 分钟 生态历史

一个问题：为什么工具这么多

如果你是最近一两年才学 Python，大概率会困惑：装个包，网上教程一会儿说 pip install，一会儿说 poetry add，最近又冒出个 uv add。它们不是同一个东西的不同名字，而是不同时代为解决不同痛点而生的产物，彼此叠加、替代，最后堆成了今天这个略显混乱的局面。

Python 包管理的历史，本质上是一条不断打补丁的路：先解决"怎么打包"，再解决"怎么装"，再解决"怎么装到隔离的环境里"，再解决"怎么让所有人装出一模一样的环境"。每一代工具，都是在给上一代工具留下的窟窿打补丁。

四个从未被真正解决、只是被逐步缓解的痛点
📦
打包标准不统一
早期没有统一的元数据格式，每个项目的 setup.py 都是一段可以任意执行的代码。
🔗
依赖解析靠运气
"能装上"不等于"版本兼容"，很长一段时间里根本没有真正的依赖解析器。
🧪
环境隔离是外挂
Python 默认把所有包装进全局环境，隔离功能是后来一层层加上去的。
🔁
无法复现
requirements.txt 记录的是"想要什么"，而不是"实际装了什么"，锁文件的概念来得很晚。
每一个新的 Python 包管理工具诞生的理由，几乎都是同一句话："上一个工具没有依赖解析器"或者"上一个工具的环境不能复现"。

时间线

八个关键节点，一路走来

下面按时间顺序梳理最重要的八个节点。不是要你记住每一个工具的用法，而是理解每一个新工具出现时，到底在解决谁的痛。

1
distutils 2000 · Python 标准库自带
Python 2.0 内置的最早的打包工具。它定义了 setup.py 这种写法——用一段 Python 代码描述"这个包叫什么、依赖谁、怎么编译"。这个设计影响了后面十几年的生态，但问题也从这里开始：元数据是代码，不是数据，工具想读取一个包的信息，必须先执行这段代码。
distutils 本身甚至不能处理依赖关系——它只管"怎么编译和安装一个包"，完全没有"这个包还需要别的包"的概念。
2
setuptools + easy_install 2004
setuptools 是 distutils 的增强版，补上了依赖声明（install_requires）、自动发现包等能力。配套的 easy_install 是第一个能自动从网上下载依赖的安装工具，在当时是很大的进步。
$
easy_install django
曾经的标准装包方式，2004–2011 年间被广泛使用
easy_install 无法卸载包、没有真正的依赖解析（版本冲突时谁装得晚谁生效）、也不支持从 requirements 文件批量安装。这些缺陷直接催生了 pip。
3
pip 诞生 2008
pip（最初叫 "pyinstall"）由 Ian Bicking 发起，专门用来解决 easy_install 的痛点：支持卸载、支持从 requirements.txt 批量安装、错误信息更清晰。2014 年之后 pip 被 CPython 内置（通过 ensurepip），从此成为事实标准。
$
pip install -r requirements.txt
批量安装，pip 带来的标志性能力
值得注意：直到 2020 年（pip 20.3），pip 才拥有真正意义上的依赖解析器。在此之前十二年里，pip 采用的是"谁先声明版本要求就用谁"的朴素策略，版本冲突经常在装完之后才暴露。
4
virtualenv 与环境隔离 2007 起普及
pip 解决了"怎么装"，但所有包默认还是装进全局 Python 环境——一台机器上的两个项目如果依赖不同版本的同一个包，就会互相冲突。virtualenv（后来 Python 3.3 起标准库内置的 venv）通过为每个项目创建独立的 Python 解释器副本，解决了这个问题。
$
python -m venv .venv
2012 年 PEP 405 之后，venv 成为标准库自带方案
这一阶段的组合拳是 "pip + virtualenv + requirements.txt"，这套三件套统治了 Python 社区将近十年，至今仍是很多老项目的标配。
5
Conda 另起炉灶 2012 · Anaconda
前面提到的 pip、virtualenv 全部只解决 Python 包本身的问题——但科学计算领域的痛点更麻烦：NumPy、SciPy 这类库背后依赖大量 C/Fortran 编译产物，在 pip 只能装纯 Python 包的年代，Windows 用户光是装一个 NumPy 就可能因为缺编译器而失败。Continuum Analytics（现 Anaconda 公司）推出 Conda，用一套完全独立于 PyPI 的二进制包仓库解决了这个问题：包里直接带上预编译好的二进制文件，不需要用户本地编译。
$
conda create -n myenv numpy scipy
环境管理 + 包管理二合一，且不局限于 Python 包
Conda 不是 pip 的替代品，而是一个平行世界：它管理的不只是 Python 包，还能装 R、CUDA、编译器这类非 Python 依赖，这也是它至今在数据科学和机器学习圈子里几乎是默认选择的原因。代价是 Conda 的包仓库和 PyPI 是两套独立体系，版本更新往往比 pip 慢，两者混用时也容易出现依赖冲突。
6
Pipenv 尝试统一 2017
requirements.txt 有个根本缺陷：它记录的是"我想要 requests>=2.0"，而不是"我实际装的是 requests==2.28.3，以及它依赖的另外 15 个包各是什么版本"。Pipenv 由 Kenneth Reitz（requests 的作者）主导，引入 Pipfile 和 Pipfile.lock，第一次把"锁文件"这个概念带进主流 Python 社区，并把 pip 和 virtualenv 合并成一个命令。
$
pipenv install requests
自动创建虚拟环境（如果还没有），并写入 Pipfile + Pipfile.lock
$
pipenv install --dev pytest
开发依赖单独分组，写入 Pipfile 的 [dev-packages] 段
$
pipenv shell
激活虚拟环境，不用再手动 source .venv/bin/activate
Pipenv 曾一度被官方 Python 打包指南推荐为首选工具，但很快因为依赖解析速度慢、维护活跃度下降而失去了社区的信任，不少团队转向了随后出现的 Poetry。
7
Poetry 与 pyproject.toml 标准化 2018
几乎同一时期，PEP 518（2016）定义了 pyproject.toml 作为构建系统声明的标准文件，PEP 621（2020）进一步把项目元数据也纳入其中。Poetry 抓住了这个标准，把依赖管理、锁文件、虚拟环境、打包发布全部整合到一个 pyproject.toml 里，并带来了一个更聪明的依赖解析器（基于 SAT 求解思路）。
$
poetry add requests
自动写入 pyproject.toml 并更新 poetry.lock
同期还有 PDM（2019）、Flit（2017）等工具，理念相近，都是"围绕 pyproject.toml、带锁文件、依赖解析更靠谱"这条路线的不同实现。
8
uv 横空出世 2024
Poetry、PDM 这一代工具解决了"正确性"，但普遍慢——用 Python 写的依赖解析器面对复杂依赖图时经常要跑几十秒。Astral（Ruff 的作者团队）用 Rust 重写了整条工具链，做出了 uv：一个同时替代 pip、pip-tools、virtualenv、Pipenv、Poetry，甚至 pyenv 的全能工具，安装速度通常比 pip 快一个数量级以上。
项目管理：一套命令覆盖从建项目到发布的全流程
$
uv init myproject
初始化项目，自动生成 pyproject.toml、README、.python-version
$
uv add requests "fastapi>=0.100"
添加依赖：自动建虚拟环境、解析版本、写入 pyproject.toml 和 uv.lock
$
uv add --dev pytest ruff
开发依赖单独分组，不会打进最终发布的包里
$
uv remove requests
移除依赖并同步更新锁文件
$
uv run python app.py
无需手动激活虚拟环境，uv 会自动同步依赖后再执行
$
uv sync
按 uv.lock 精确重建环境，用于 CI 或新同事拉取代码后的第一步
顺带取代的另外两个工具
$
uv python install 3.12
下载并管理 Python 解释器本身，相当于替代了 pyenv
$
uv tool install ruff
把命令行工具装到独立隔离环境，相当于替代了 pipx
uv 依然使用标准的 pyproject.toml，这也是它能被快速接受的原因之一——它不是又发明一套新格式，而是把已有的标准执行得更快。它还完全兼容 pip 的命令习惯，老项目可以直接用 uv pip install -r requirements.txt 无缝替换，不用一次性重构成新的项目结构。

对比

今天常见的几种工具，各自的定位

工具对比
工具核心特点依赖解析锁文件
pip 最基础、最通用，几乎所有 Python 环境都有 2020 年后有 较好 无（需配合 pip-tools）
Conda 独立于 PyPI 的二进制仓库，能装非 Python 依赖 较好，但与 PyPI 生态割裂 environment.yml
Pipenv pip + virtualenv 的早期整合方案 较慢 性能弱 Pipfile.lock
Poetry 依赖管理 + 打包发布一体化，生态成熟 较好，但复杂依赖图偶尔慢 poetry.lock
PDM 紧跟 PEP 标准，支持 PEP 582 免虚拟环境模式 较好 标准化 pdm.lock
uv Rust 编写，速度极快，意在统一整条工具链 快且准确 领先 uv.lock

这里没有绝对的"最好"。老项目和大量遗留代码依然只依赖 pip + requirements.txt；新项目如果追求速度和现代化体验，uv 是目前的热门选择；如果团队更看重生态成熟度和文档，Poetry 依然是稳妥的选项。

操作习惯对照：Conda / Poetry / uv
你想做什么CondaPoetryuv

指定 Python 版本 conda create -n myenv python=3.11 在 pyproject.toml 里声明 python = "^3.11" uv venv --python 3.11（会自动下载对应版本）

安装依赖（复现环境） pip install -r requirements.txt poetry install uv sync

如果你现在的习惯是"conda 建环境 + 全程只用 pip 装包"，那基本可以直接对照上表切到 Poetry 或 uv，功能上是平替，还多了锁文件；只有真的需要装非 Python 的二进制依赖（CUDA、科学计算库等）时，才有必要继续留着 Conda。「安装依赖」这一行尤其值得注意：requirements.txt 记录的是版本范围，同一份文件不同时间跑可能装出不同的小版本；而 uv sync / poetry install 靠的是锁文件，装出来的版本永远和锁文件里写死的完全一致，这也是锁文件机制真正的价值所在。

标准

背后真正起作用的，是一系列 PEP

工具会换，但推动这些工具演进的标准才是真正的主线。理解这几个 PEP，就能理解为什么今天所有新工具都长得越来越像。

关键 PEP 一览
PEP年份解决了什么
PEP 4272012定义 wheel 格式，取代慢得多的从源码构建（sdist）
PEP 5182016引入 pyproject.toml，声明构建系统依赖
PEP 5172017定义标准的构建后端接口，工具不再互相绑定
PEP 6212020把项目元数据（名称、版本、依赖等）也标准化进 pyproject.toml
PEP 6682023标记"外部管理"的环境，防止 pip 意外污染系统 Python
如果说前二十年的 Python 打包史是"每个工具各自为战"，那么 pyproject.toml 系列 PEP 做的事情，是第一次让所有工具围绕同一份标准文件说话。

现状建议

新项目该怎么选

如果你现在要开一个新项目，不用纠结历史包袱，直接按下面的思路选就好。

简单决策参考
🚀
追求速度和简洁
用 uv。它兼容 pip 的大部分命令习惯，又快又新，社区增长最快。
📚
团队更看重成熟稳定
用 Poetry。生态、插件、文档都非常完善，出问题容易查到解决方案。
🧬
做数据科学 / 机器学习
优先考虑 Conda（或 mamba），省去手动编译 NumPy/CUDA 这类二进制依赖的麻烦。
🏛️
维护老项目 / 极简需求
继续用 pip + venv 完全没问题，不必为了"追新"而重构整个项目。
⚠️
尽量避免
easy_install 早已停止维护，Pipenv 活跃度持续走低，新项目不建议再选它们。

不管选哪个工具，只要项目的元数据和依赖最终落在 pyproject.toml 里，你就已经站在了标准这一边——未来即使换工具，迁移成本也会小很多。Conda 是唯一的例外：它服务的是"非 Python 依赖"这个 pyproject.toml 体系目前还没打算解决的问题，两条线大概率会长期并存。
