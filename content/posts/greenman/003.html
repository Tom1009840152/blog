产品经理的专业语言

PM 说的"北极星指标""用户旅程""MVP"到底是什么意思？读完这篇，下次需求评审你能听懂每一句话。

2026-06-05 阅读约 12 分钟 产品思维 · PM 术语 建议先读第一、二篇

产品经理是离用户最近的角色，也是需求的起点。他们有一套独特的语言，用来描述"用户是谁""用户要什么""怎么衡量做得好不好"。

这套语言分四个层次：想清楚要做什么，写清楚怎么做，衡量做得好不好，以及规划下一步做什么。我们依次来看。

第一层

想清楚要做什么——用户研究语言

在写任何一个字的需求文档之前，产品经理要先想清楚：这个功能是给谁做的，他们遇到了什么问题，我们要解决哪一个。这一层的词，是产品思考的基础单元。

用户研究相关术语
用户画像 User Persona

对目标用户群体的虚构化描述，包括年龄、职业、行为习惯、痛点，帮助团队在讨论时"对着同一个人说话"。

「这个功能的核心用户画像是 25-35 岁的上班族，每天通勤 1 小时，碎片化时间多。」

痛点 Pain Point

用户在当前体验中感到不满、困难或低效的地方，是产品要解决的问题根源。

「用户最大的痛点不是功能少，是每次找不到上次的记录。」

使用场景 Use Case / Scenario

用户在什么时间、什么地点、什么状态下使用这个功能，场景决定了功能的设计边界。

「主要场景是用户在等电梯的时候，所以操作步骤不能超过两步。」

用户故事 User Story

用一句话从用户视角描述需求的格式：作为 [谁]，我想要 [做什么]，以便 [达到什么目的]。强迫需求回归用户视角，避免"为做而做"。

「把这个需求写成用户故事，我们再对齐一下出发点。」

用户故事的格式值得单独看一眼，因为你在评审会上会频繁听到 PM 用这个格式表达需求：

用户故事示例 · 签到功能
作为 一个每天使用 App 的用户，
我想要 每天签到并获得积分奖励，
以便 积累足够的积分后兑换优惠券，感受到坚持使用的价值。
作为 一个已连续签到 6 天的用户，
我想要 看到"再坚持 1 天即可获得额外奖励"的提示，
以便 获得足够的动力不中断连续签到。

注意：同一个功能可以写出多个用户故事，对应不同的使用场景和用户状态。

了解用户画像之后，产品经理还需要选择先做什么。这时会用到两个重要概念：

用户画像示例 · 签到功能目标用户
👨‍💼

通勤族小陈

28 岁 · 互联网从业者

场景早晚各 40 分钟地铁通勤，刷手机打发时间
痛点用 App 很频繁，但没有"坚持"的理由
诉求用积分换咖啡券，性价比感强
👩‍🎓

21 岁 · 在校学生

场景课间休息、睡前，随时随地
痛点每天打开 App 但没什么特别的动力

关键概念

MVP——先做多少才够？

产品经理最常被追问的问题之一就是"这期到底做哪些功能"。MVP 是回答这个问题的核心工具。

MVP 相关术语
MVP Minimum Viable Product

最小可行产品——只做核心功能、能跑通主流程的最简版本，用最小成本验证假设，再决定要不要继续投入。

「先做个 MVP 上线，验证用户真的会每天来签到再说后面的复杂逻辑。」

范围蔓延 Scope Creep

开发过程中需求不断被追加，导致项目越做越大、无法按时交付的现象，是 MVP 思维要对抗的敌人。

「我们要注意范围蔓延，这期只做签到核心流程，分享功能放下期。」

签到功能的 MVP 拆分示例：

✅ MVP
签到 + 积分发放
v1.1
连续签到提醒
v2.0
成就 + 分享
v3.0
社群排行
MVP 不是"做一个烂版本"，
是"做一个对的版本，只是功能少"。

第二层

写清楚怎么做——文档与设计语言

想清楚之后，产品经理要把想法变成文字和原型，让研发和测试能够理解并执行。

文档与设计相关术语
原型 Prototype / Wireframe

功能的可视化草图，可以是线框图（低保真）或接近真实 UI 的交互稿（高保真），让研发和设计看到功能"长什么样"。

「原型我发群里了，你们研发先看看有没有实现上的问题。」

交互说明 Interaction Spec

描述用户操作后系统应该如何响应的细节，比如"点击签到按钮后，动画播放 0.3 秒，积分数字滚动增加"。

「这里的交互说明没写清楚，按钮 loading 状态要持续多久？」

边界条件 Edge Case

非正常路径下的情况，比如"用户网络断了""积分已达上限""同一账号在两台设备同时签到"，PRD 必须覆盖否则留下 bug 隐患。

「这个边界条件没写：用户改了时区，签到时间怎么算？」

主流程 / 异常流程 Happy Path / Error Path

主流程是一切顺利时用户走过的路径；异常流程是出错、中断、权限不足等情况下的处理逻辑，两者都要写清楚。

「主流程写清楚了，但签到失败的异常流程还没有说明。」

验收标准 Acceptance Criteria

明确列出"怎样才算做完"的条件清单，是测试用例的来源，也是产品验收时的判断依据。

「PRD 里要加上验收标准，不然研发和测试的理解会不一样。」

第三层

衡量做得好不好——数据指标语言

功能上线之后，产品经理要用数据回答一个问题：这个功能有没有达到预期效果？这需要一套指标体系。

核心数据指标

日活跃用户

DAU

每天打开 App 至少一次的用户数，衡量产品的日常活跃程度

月活跃用户

MAU

每月内有过活跃行为的用户数，衡量产品的中期规模

次日留存率

D1 留存

今天新来的用户，明天还回来的比例，是衡量产品黏性最重要的指标之一

7 日留存率

D7 留存

7 天后还在用的用户比例，判断用户是否真正养成了使用习惯

用户流失率

Churn Rate

在某段时间内停止使用产品的用户占比，留存的反面

转化率

CVR

完成某个目标动作（如注册、购买、签到）的用户占进入该流程用户的比例

其他重要指标术语
北极星指标 North Star Metric

整个产品或团队最核心的单一成功指标，所有工作都围绕它展开。之所以叫"北极星"，是因为它给出方向，其他指标都要服务于它。

「我们这个季度的北极星指标是 D7 留存率，签到功能就是为了提升它。」

转化漏斗 Conversion Funnel

把用户完成某个目标的全过程拆成多步，观察每一步的流失情况，找到最需要优化的断点。形状像漏斗，越往下人越少。

「从首页到签到完成的转化漏斗数据出来了，第二步流失 40%，有问题。」

A/B 测试 A/B Test

同时向不同用户群展示两个不同版本（A 和 B），用数据对比决定哪个更好，而不是靠主观判断。

「我们做个A/B 测试，一组签到按钮红色、一组蓝色，看哪个点击率高。」

埋点 Event Tracking

在代码里记录用户行为事件（如"点击签到按钮"）的技术手段，是所有数据分析的前提。没有埋点，就没有数据。

「签到按钮要加埋点，把点击时间和用户 ID 都记下来，方便后续分析。」

转化漏斗值得单独看一眼，因为 PM 在汇报和复盘时几乎必然会用到它：

转化漏斗示例 · 签到完成流程
打开 App
100,000 人
点击签到入口
72,000 · 72%
进入签到页面
43,000 · 40%流失 ⚠
完成签到
38,000 · 88%

第二步到第三步流失了 40%，说明"点击入口"到"进入页面"之间有体验问题，可能是加载太慢或跳转路径不清晰，需要重点排查。

第四层

规划下一步——产品战略语言

产品经理不只管眼前这个版本，还要规划未来的方向。这一层的词，是在做更大时间尺度的决策时用的。

产品规划相关术语
Roadmap Product Roadmap

产品未来一段时间（通常是 3～12 个月）的功能规划路线图，说明什么时候做什么，大方向是什么。

「Q3 的 Roadmap 还没出，我们先别排太远的需求。」

用户旅程 User Journey Map

把用户从"知道这个产品"到"离开这个产品"的完整经历可视化，每个阶段的行为、情绪、痛点都标出来，找到最需要改善的节点。

「我们画一下新用户的用户旅程，看注册后第一周他们的体验是什么样的。」

AARRR 模型 Pirate Metrics

增长黑客领域经典的用户生命周期模型，把用户分成五个阶段，帮助产品找到每个阶段的增长抓手。

「我们现在的问题在 AARRR 的 Retention 阶段，留存太低。」

版本规划 Version Planning

把功能按重要程度和依赖关系分配到不同版本（v1.0、v1.1、v2.0），平衡用户价值和开发成本。

「这个功能放 v2.0 吧，现在做太复杂，先把 v1.0 的核心路径跑通。」

AARRR 模型拆解
A Acquisition
用户获取 用户怎么来的？广告、搜索、口碑、应用商店……这个阶段关注新用户数量和获客成本
A Activation
用户激活 用户来了之后有没有完成"第一次有价值的体验"？比如注册、完成首次签到
R Retention
用户留存 ← 重点 用户有没有养成回来的习惯？签到功能就是专门提升这个阶段的工具
R Revenue
商业变现 用户有没有产生收入？付费、广告点击、积分兑换消费……
R Referral
用户推荐 用户有没有主动推荐给别人？口碑裂变、邀请好友……
