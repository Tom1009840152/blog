HTTP 请求全解析

打开网页、调用 API、发送表单——这些操作背后都是一次 HTTP 请求。它的结构比你想象的简单，弄懂它，你会对整个互联网的运作方式有全新的认识。

2026-07-08 阅读约 6 分钟 HTTP · 请求头 · 请求体 · REST API 无需基础

你打开浏览器，输入一个网址，按下回车——不到一秒，网页出现了。这中间发生了什么？答案是：你的浏览器向服务器发送了一条消息，服务器收到后把网页内容回传给你。这条消息，就叫做 HTTP 请求。

调用 API 时用的 curl 命令、手机 App 刷新动态、网页里的登录按钮——本质上都是同一件事：构造一个 HTTP 请求，发出去，等回应。

基本概念

HTTP 是什么：客户端和服务器的"对话规则"

HTTP 全称 HyperText Transfer Protocol（超文本传输协议）。"协议"这个词听起来很正式，其实就是双方说话的格式约定——你按这个格式发消息，对方才能看懂；对方也按这个格式回复，你才能解析。

HTTP 对话的完整流程
你（客户端）浏览器 / App / curl
——请求——→
互联网传输
——→
服务器处理并返回数据
你收到响应网页 / JSON / 图片
←——响应——
互联网传输
←——
服务器200 OK / 404 / 500…

这套"一问一答"的模式，专业上叫做请求-响应模型。本文重点讲"请求"这半边——你发出去的那条消息长什么样。

请求结构

一次请求由四部分组成

一个 HTTP 请求就像一封信——有信封上的地址（URL）、寄件方式（方法）、附带说明（请求头），以及信件正文（请求体）。四个部分各司其职，缺一不可（当然，有些请求不需要正文）。

HTTP 请求完整结构
请求行
POST /api/v1/users HTTP/1.1
方法 + 路径 + HTTP 版本，固定在第一行
请求头
Authorization: Bearer sk-xxxx
Content-Type: application/json
Accept: application/json
键值对，传递元信息：身份、数据格式、偏好……
空行
（固定空行，分隔头和体，不可省略）
请求体
{"name": "张三", "age": 18}
实际数据，POST / PUT 才有；GET 通常没有

对应到 curl 命令：-X POST 是方法，URL 是路径，--header 是请求头，--data 或 -d 是请求体。四个部分一一映射，curl 只是把它们翻译成了命令行语法。

四种参数

URL、路径、查询、请求体：数据放哪里有讲究

新手最容易混淆的是"参数放哪"这个问题。一次请求里，数据其实可以藏在四个不同的位置，每个位置的含义和用途都不一样。

四种参数位置对比
位置 示例 典型用途 出现在哪
路径参数 /users/123 指定"操作的是哪个资源" URL 路径里 Path
查询参数 /users?page=2 筛选、分页、排序等过滤条件 URL 的 ? 后面 Query
请求头参数 Authorization: Bearer sk-xxxx 身份认证、数据格式声明 Headers 区域 Header
请求体参数 {"name": "张三"} 新建或更新时传递的具体数据 Body 区域 Body
路径参数说"找谁"，查询参数说"怎么找"，
请求头说"我是谁"，请求体说"要做什么"。

以一个完整的请求为例，四种参数同时出现长这样：

四种参数同时出现的完整示例
# 给用户 123 的订单列表新增一条，并按时间排序查询第 2 页 POST /api/v1/users/123/orders?sort=time&page=2 ← 路径参数(123) + 查询参数 Authorization: Bearer sk-xxxx ← 请求头：身份认证 Content-Type: application/json ← 请求头：声明Body格式 ← 空行 { ← 请求体：新增的数据 "product_id": "abc-001", "quantity": 2 }

请求方法

GET / POST / PUT / DELETE：动词决定意图

HTTP 方法（也叫"动词"）告诉服务器你想做什么操作。常见的四种方法对应了对数据的四种基本操作，合称 CRUD——增删改查。

四种常用 HTTP 方法

GET — 查询

取数据，不改变服务器状态。浏览器打开网页、查询任务状态，都是 GET。通常没有请求体。

POST — 新建

提交数据，创建新资源。提交表单、注册账号、上传文件，一般用 POST。数据放在请求体里。

PUT / PATCH — 修改

更新已有资源。PUT 是整体替换，PATCH 是局部更新。数据同样放在请求体里。

DELETE — 删除

删除指定资源。路径里带上资源 ID，告诉服务器删哪个。通常也没有请求体。

记忆技巧：GET 是"给我看看"，POST 是"我要提交"，PUT 是"帮我改掉"，DELETE 是"把它删了"。方法只是约定，服务器怎么实现取决于 API 设计——但大多数规范的 API 都遵循这套语义。

常见请求头

请求头不神秘：几个高频字段全解析

请求头（Headers）是一组键值对，夹在请求行和请求体之间，负责传递各种"元信息"。以下是你会最频繁碰到的几个：

高频请求头字段速查
字段名 示例值 作用
Authorization Bearer sk-xxxx 身份认证，携带 Token 或 API Key，证明"我是谁"
Content-Type application/json 声明请求体的格式，告诉服务器"我发的是 JSON"
Accept application/json 告诉服务器"我希望你返回 JSON 格式"
User-Agent Mozilla/5.0… 标识客户端类型（浏览器 / App / curl），服务器可据此区别处理
Cookie session=abc123 携带浏览器存储的会话信息，用于保持登录状态

其中 Authorization 是调用 API 时最常用的。格式 Bearer <token> 是业界标准写法：Bearer 是固定前缀（表示"持有者令牌"），后面跟你的实际 token。缺少这个头，服务器会拒绝请求并返回 401 Unauthorized。

小结：Content-Type 告诉服务器"我发的什么格式"，Accept 告诉服务器"我要什么格式"，Authorization 告诉服务器"我是谁"。三个头各管一件事，搭配使用就能应对绝大多数 API 场景。

实战拆解

读懂一条真实的 curl 请求

理论说完，来看一条真实世界里的 API 请求，把每个部分都对应起来：

完整 curl 请求拆解
curl -X GET \ ← 请求方法：查询 https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com \ ← 服务器地址 /api/v1/tasks/{task_id} \ ← 路径参数：查哪个任务 --header "Authorization: Bearer $DASHSCOPE_API_KEY" ← 请求头：身份认证

这是一个 GET 请求，没有请求体——因为只是查询，不需要提交数据。
唯一的请求头是 Authorization，携带 API Key 做身份验证。
{task_id} 是路径参数，使用时替换为真实的任务 ID。

为什么接口文档里有时只有"请求头"和"路径参数"两种？因为 GET 查询接口逻辑简单：知道"查谁"（路径参数）、证明"是谁在查"（请求头）就够了。不同接口按需使用，不是每次都要全部四种参数都出现。
