Git 工作流：
从零到第一个 PR

每个写代码的人迟早都要面对 Git。这篇文章从最实际的角度出发——拉代码、切分支、提交、发 PR——带你走完一次完整的协作流程。

2026-06-23 阅读约 5 分钟 新手向

Git 是什么，为什么要用它

Git 是一个分布式版本控制系统，说白了就是帮你记录代码每次改动的工具。你改了什么、什么时候改的、谁改的——全部都有记录，随时可以回滚。

在团队里，每个人都在同一个代码库里工作。没有 Git，两个人同时改同一个文件，最后只有一个人的版本能留下来。Git 解决的核心问题是：让多人协作不互相踩脚。

为什么要用 Git
🔄
任意回滚
每次 commit 都是一个快照，改坏了可以随时回到之前任意一个版本。
🌿
分支隔离
每个功能在自己的分支上开发，互不干扰，完成后再合并进主线。
👥
多人协作
十个人同时改同一个项目，Git 负责把各自的修改安全地合并在一起。
🔍
追溯历史
任何一行代码是谁改的、什么时候改的、为什么改——一查就知道。
Git 的核心思想：不要在原地改，先开一个分支，改完了再合并。这一个习惯，能避开协作里 90% 的麻烦。

完整流程

从拉代码到发 PR，六步走完

下面把整个工作流拆成六步，每步都有具体命令和说明，按顺序走一遍就是一次完整的功能开发。

1
拉取最新代码
每次开始工作的第一件事：把远端 main 的最新内容同步到本地，避免和别人已提交的内容冲突。
$
git checkout main
先切回主分支
$
git pull origin main
从远端拉取最新内容，看到 "Already up to date." 就说明同步成功
很多新手会跳过这一步，结果改完代码发现和别人的版本差了好几天，冲突一大堆。养成习惯，每次开工前先 pull 一次。
2
创建并切换到自己的分支
拉完代码立刻开一个新分支，在这个分支上做修改。永远不要直接在 main 上改代码，这是团队协作最基本的规则。
$
git checkout -b feat/user-login
-b 表示新建并切换；换成你自己的分支名
$
git branch
确认当前分支，带 * 的就是你所在的
分支命名约定：feat/功能名 新功能 · fix/描述 修 bug · chore/描述 配置杂项 · docs/描述 文档
3
修改代码
在这个分支上放心改。随时可以用下面两个命令检查自己的改动情况。
$
git status
查看哪些文件被修改、新增或删除了
$
git diff
查看具体改了哪些行，红色是删除，绿色是新增
4
暂存并提交
改完之后，先 git add 把文件放进暂存区，再 git commit 正式保存成一个快照。commit message 要写清楚做了什么。
$
git add .
把所有改动加入暂存区；也可以指定单个文件
$
git commit -m "feat: 添加用户登录页面"
引号里写这次改动做了什么，给未来的自己和队友看
commit message 好坏对比
质量示例
好feat: 添加邮箱登录，支持记住密码
好fix: 修复首页按钮在 Safari 下点击无响应
差update — 什么都没说
差fix bug — 哪个 bug？
5
推送到远端
commit 只保存在本地，队友还看不到。需要把分支推到 GitHub/GitLab，才能在上面发起 PR。
$
git push -u origin feat/user-login
第一次推这个分支加 -u，建立追踪关系
$
git push
之后在同一分支继续提交，直接这样推就够了
推送成功后，终端会打出一个链接，点击直接跳到创建 PR 的页面。
6
发 PR，请人 Review
PR（Pull Request）是一个正式的请求：告诉队友"我改好了，请帮我看一下，没问题就合并进 main"。这是代码质量的最后一道关。
怎么进到这个页面？有两种方式：
① 终端直接给你链接：git push 成功后，终端最后几行会打出一条 https://github.com/…/compare/feat/xxx… 链接，点击直接跳转到创建 PR 的页面。
② 手动进入：打开 GitHub 仓库主页，顶部会出现一个黄色提示条 "Compare & pull request"，点击即可；或者点导航栏 Pull requests → New pull request，手动选择你的分支。
github.com / your-org / repo / pull / 42
feat: 添加用户邮箱登录功能
● Open base: main ← feat/user-login
改动说明
实现邮箱 + 密码登录，支持"记住我"（7 天 token）。登录成功跳转 /dashboard，失败时显示具体错误提示。
测试方式
npm run dev → 访问 /login → 用 test@example.com / password123 验证登录流程。
自查清单
  • ✓ 本地测试通过
  • ✓ 没有遗留 console.log
  • ○ 需要 Reviewer 确认 token 过期策略
AZ
Reviewer: @alice-zhang ● Awaiting review
Reviewer 留了 Comments 不要慌——这是正常流程。改完后在对应 Comment 下回复"已处理"，然后点 Re-request review。不要自己直接 Merge，等 Approve 之后再合并。

常见问题

新手最常遇到的几个坑

问题与解决方法
问题原因解决
push 被拒绝 远端有别人新推的 commit，本地落后了 先 git pull，处理冲突后再 push
出现 merge conflict 你和别人改了同一文件的同一处 打开冲突文件手动选择，然后重新 add + commit
提交了不该提交的文件 没配 .gitignore，把 node_modules 或 .env 提交进去了 加好 .gitignore，用 git rm --cached 移除追踪
commit message 写错了 —— 还没 push 的话，用 git commit --amend 修改

遇到不认识的报错，把完整报错信息直接搜索，99% 都能找到答案。Git 的错误提示很详细，大多数情况下它自己就会告诉你怎么修复。
