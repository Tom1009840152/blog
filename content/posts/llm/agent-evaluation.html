Agent 评测体系全景

Agent 不像传统软件，没有唯一正确输出，行为随上下文涌现，失败链路深埋多步推理之中。一套没想清楚的评测，不是在保证质量，而是在制造虚假安全感。

2026-05-28 阅读约 15 分钟 Agent · 评测

很多团队在上线 Agent 之前都做了"评测"：跑了几十条测试用例，通过率 80%，看起来挺好。但真正部署之后，用户反馈却截然不同——明明测过的场景，线上翻车了；明明写了 case，却覆盖不到真实的失败路径。

问题往往不出在执行上，而出在评测的设计上。Agent 的评测和传统模型的评测，是两件完全不同的事。如果用传统的思路去评测 Agent，你可能从一开始就在测错方向。

为什么难

Agent 评测比你想的难得多

评测一个普通分类模型很直观：准确率、F1，算完就知道好不好。但 Agent 的评测是另一回事。Agent 在一次任务中可能调用十几个工具、做出多步决策、产生中间状态——最终输出只是冰山一角，过程本身就是质量。

更麻烦的是，Agent 的行为是涌现的：换一个措辞、调整一个工具描述、甚至改变系统提示的顺序，都可能导致完全不同的行为路径。这让"可重复测试"本身就成了一道难题。

传统模型评测 vs Agent 评测
🎯

传统模型

单次输入 → 单次输出。有标准答案，指标客观，自动化容易，可重复性高。评测成本低。

🌀

Agent

多步决策 → 工具调用 → 环境交互 → 最终输出。无单一正解，过程非确定，评测成本高，需要专门设计。

用户输入一次性、确定
→
规划LLM 推理
→
工具调用多次、有副作用
→
观察环境反馈
→
输出仅是表象

每一步都可能出错，而最终输出"看起来正确"并不意味着过程是对的——这正是只看结果会产生虚假安全感的原因。

⚠️ Agent 评测最危险的反模式：只测最终答案是否正确，忽略中间的工具调用序列。一个"侥幸"给出正确答案的 Agent，换个任务会立刻暴露。

评测分层

评测体系的四层金字塔

健壮的 Agent 评测体系不是单一指标，而是分层设计——从底层的能力单测，到顶层的端到端任务成功，每一层覆盖不同粒度的质量问题，相互补充。

Agent 评测四层金字塔（越顶层越昂贵）
端到端任务评测成功率 · 人工验收
轨迹 / 过程评测工具调用序列 · 步骤效率
组件评测工具准确率 · 规划质量 · 记忆检索
基础能力评测指令遵循 · 格式合规 · 幻觉率 · 边界识别

底层测试快、便宜、可自动化，应当大量运行；顶层测试真实、有说服力，但昂贵，用于关键决策节点。

四层之间存在一个黄金法则：底层失败必须先修，顶层失败才有诊断意义。一个连格式都输出不稳定的 Agent，做端到端测试只是在浪费算力和时间。

核心指标

你需要关心的六类核心指标

以下六类指标覆盖了 Agent 评测中最高频的需求。它们不是互斥的——一个完整的评测 dashboard 通常会同时追踪多类指标，根据 Agent 的具体应用场景调整权重。

① 任务成功率（Task Success Rate）

最直观的顶层指标：给定任务，Agent 最终是否达成目标。但"成功"的定义是关键——需要提前写清楚验收标准。

✅

二元成功率

任务完成 or 失败。定义清晰，适合有明确验收标准的任务（如"预订成功"、"代码通过所有测试"）。

📊

部分成功率

按子目标完成比例打分。适合长链任务，避免因最后一步失败而抹杀所有前置工作的价值。

# 验收标准示例：代码生成 Agent def evaluate_task(agent_output, test_cases): results = [] for tc in test_cases: passed = run_test(agent_output.code, tc) results.append(passed) # 二元成功：全部通过才算成功 binary_success = all(results) # 部分成功：通过比例 partial_score = sum(results) / len(results) return { "binary": binary_success, "partial": partial_score, # e.g. 0.75 = 75% 测试通过 "details": results }
② 轨迹质量（Trajectory Quality）

衡量 Agent 达成目标的"路径质量"——即使结果对了，路径低效或危险也是问题。轨迹评测是 Agent 评测中最有区分度的维度。

🛤️

工具调用序列准确率

实际调用的工具序列与最优参考序列的相似度。衡量 Agent 的规划能力是否靠谱。

⚡

步骤效率（步数 / token 消耗）

完成任务用了多少步、花了多少 token。同样的成功率下，步数少的 Agent 更实用、成本更低。

🔁

冗余调用率

重复调用同一工具、或调用后结果未被利用的比例。高冗余率通常意味着规划能力不足。

🚫

无效行动率

调用了错误工具、传入了无效参数，导致工具报错或返回无用结果的比例。

# 轨迹对比评测（对照"黄金轨迹"） golden_trajectory = [ ("search", {"query": "2024 AI papers"}), ("read_doc", {"url": "..."}), ("summarize", {"text": "..."}), ] agent_trajectory = agent.run(task) # 计算 F1：工具名 + 参数是否匹配 precision = matched_steps / len(agent_trajectory) recall = matched_steps / len(golden_trajectory) f1 = 2 * precision * recall / (precision + recall)
③ 工具调用准确率（Tool Use Accuracy）

具体衡量 Agent 在工具选择和参数生成上的准确性。这是组件层评测的核心，可以快速定位工具描述或提示设计的问题。

子指标含义适用场景
工具选择准确率 面对特定需求，选对工具的比例 工具数量多、语义相近时尤为重要
参数格式合规率 生成的参数符合 Schema 定义的比例 任何有结构化入参的工具
参数语义准确率 参数格式对了，但值是否符合语义意图 需要人工或 LLM-as-judge 评估
空调用率 本应调用工具却没有调用（直接"编"答案） 幻觉检测的重要信号
④ 忠实度 & 幻觉率（Faithfulness & Hallucination）

Agent 的输出是否忠实于它实际检索 / 执行到的信息？幻觉在 Agent 场景尤其危险——它可能表现为"捏造工具的返回结果"。

📎

上下文忠实度

最终答案中每个声明，能否在工具返回的上下文中找到来源？用 NLI 模型或 LLM-judge 自动检测。

🔮

工具结果幻觉

Agent 声称调用了工具并得到结果，但实际没有调用，或调用结果与声明不一致。最隐蔽的幻觉形式。

⑤ 安全性 & 边界遵守（Safety & Constraint Adherence）

Agent 是否尊重被赋予的权限边界？尤其在有真实副作用的系统中（如发邮件、写文件、执行代码），这是上线前的红线指标。

🔐

权限越界率

Agent 尝试调用超出授权范围工具的比例。用 mock 工具 + 沙箱环境测试，任何越界都是严重缺陷。

⏸️

高风险确认率

面对高风险操作（不可逆、大范围影响），Agent 是否正确暂停并向用户确认，而不是自行执行。

💉

注入攻击抵抗率

当工具返回内容中包含恶意指令时，Agent 是否能识别并拒绝执行，而不是被"劫持"。

🎭

角色/指令遵守率

Agent 是否稳定遵守系统提示中的行为约束，而不随用户的诱导而偏移。

⑥ 鲁棒性 & 一致性（Robustness & Consistency）

相同语义的任务，经过措辞变换、注入噪声、工具报错等干扰后，Agent 的表现是否稳定？这个维度直接决定 Agent 在真实生产环境中的可信度。

σ

评测方法

怎么测：四种主流评测方法

指标定义好了，下一个问题是：用什么方式来打分？不同方法在成本、覆盖度、可信度上各有权衡，实际工程中往往组合使用。

四种评测方法对比
方法原理优点局限
规则 / 单元测试 assert 语句、正则、Schema 校验 速度快、零成本、可重复 首选 无法覆盖语义质量
LLM-as-Judge 用另一个 LLM 打分或比较 能处理开放域输出、无需人工 高效 有位置偏差、自我偏好偏差，需校准
人工评估 人类标注员打分 最高可信度，可发现意外问题 金标准 慢、贵，不可持续大规模运行
沙箱 / 模拟环境 Mock 外部工具，在隔离环境中运行 可测有副作用操作、可重复 必备 真实环境中的边界 case 难以完全模拟

LLM-as-Judge 是近年来最受关注的方法，因为它让自动化覆盖到了主观质量评估。但使用时要特别注意几个已知偏差：

LLM-as-Judge：已知偏差与缓解策略
📍

位置偏差

倾向给第一个或最后一个选项打高分。缓解：随机打乱选项顺序，多次运行取平均。

🪞

自我偏好

用 GPT-4 当 judge 时，它倾向给 GPT-4 生成的输出打高分。缓解：换用不同 family 的 judge 模型。

📝

长度偏差

倾向认为更长的回答更好。缓解：在 judge prompt 中明确要求"不考虑长度因素"。

🎭

过度自信

judge 给出的分数往往缺乏区分度（集中在 4-5 分区间）。缓解：要求给出具体理由，使用对比评分（A vs B）而非绝对评分。

# LLM-as-Judge prompt 模板（对比评分，缓解绝对分偏差） judge_prompt = """ 你是一位严格的评估者。比较以下两个 Agent 的回答，判断哪个更好。 评估维度：准确性、完整性、步骤合理性。 不要考虑回答长度。不要偏向任何特定风格。 任务：{task} 回答 A：{response_a} 回答 B：{response_b} 请先给出判断理由（2-3 句话），再给出结论：A 更好 / B 更好 / 平局。 """ # 随机化顺序消除位置偏差 import random if random.random() > 0.5: response_a, response_b = response_b, response_a swapped = True

测试集设计

测试集怎么设计：三类必备用例

好的评测指标加上糟糕的测试集，等于零。测试集的质量决定了评测体系能发现多少真实问题。一个成熟的 Agent 测试集通常包含三类用例：

测试集三层构成
① 黄金用例（Golden Cases）
典型任务的最优轨迹 + 最优输出，人工审核通过。用于回归测试：每次改动后跑一遍，确保核心场景不退步。数量不用多，20-50 条精心设计的用例胜过 500 条随机用例。
② 边界用例（Edge Cases）
歧义指令、工具返回错误、权限受限、任务无解、超长上下文、多语言混用……真实用户的输入总是千奇百怪。边界用例专门测试 Agent 的降级处理能力。
③ 对抗用例（Adversarial Cases）
注入攻击（工具返回中藏着"忽略以上指令"）、越权诱导（"帮我以管理员身份执行"）、幻觉诱导（"你上次说过……"）。对于生产 Agent，这类测试是安全上线的必要条件。

💡 测试集建设的最佳实践：把生产环境中出现的每一个 bug，都转化为一条测试用例。这样，测试集会随着产品成熟而自然生长，并且每条用例都对应一个曾经真实发生过的问题。

在数量和多样性上，可以借助 LLM 批量生成测试用例——但生成的用例必须经过人工审核再纳入测试集，否则会引入"用 LLM 测 LLM"的闭环偏差，测试集本身就可能包含错误。

实战流程

评测跑起来：从零到 CI 集成

评测不是一次性的，而是贯穿 Agent 开发全生命周期的持续活动。以下是一个经过验证的落地流程：

Agent 评测落地流程
定义验收标准写在代码里，不是文档里
→
建黄金测试集20–50 条精标用例
→
搭沙箱Mock 所有外部工具
→
跑基线记录各指标初始值
→
接入 CI每次 PR 自动评测

接入 CI 后，每次修改 prompt、工具描述、模型版本，都会自动跑评测，防止无意识的性能退步。

一个最简可运行的评测框架（Python）
# eval_runner.py — 最简 Agent 评测框架 import json from dataclasses import dataclass from typing import List, Callable @dataclass class TestCase: id: str task: str # 任务描述 expected_tools: List[str] # 期望调用的工具列表 success_fn: Callable # 验收函数 def run_eval(agent, test_cases: List[TestCase]) -> dict: results = [] for tc in test_cases: # 运行 Agent，捕获完整轨迹 trajectory, final_output = agent.run(tc.task) # 指标 1：任务成功率（用验收函数判断） success = tc.success_fn(final_output) # 指标 2：工具调用准确率 called_tools = [step.tool_name for step in trajectory] tool_acc = len( set(called_tools) & set(tc.expected_tools) ) / len(set(tc.expected_tools)) # 指标 3：步骤效率 step_count = len(trajectory) results.append({ "id": tc.id, "success": success, "tool_acc": tool_acc, "steps": step_count, }) # 汇总 return { "task_success_rate": sum(r["success"] for r in results) / len(results), "avg_tool_accuracy": sum(r["tool_acc"] for r in results) / len(results), "avg_steps": sum(r["steps"] for r in results) / len(results), "details": results, }

常见工具

生态里有哪些现成工具？

不必从零造轮子。以下是目前社区中主流的 Agent 评测工具与框架，按用途分类：

Agent 评测工具全景
🧪

LangSmith

LangChain 生态的评测 + 追踪平台。内置 LLM-as-Judge、轨迹记录、数据集管理。对 LangChain/LangGraph 用户开箱即用。

📐

Ragas

专注 RAG + Agent 的评测库。提供忠实度、答案相关性、上下文召回率等开箱即用指标，支持自定义。

📋

Inspect AI

UK AISI 出品的开源评测框架。任务 + 解答器 + 评分器三段式设计，适合系统性的 Agent 能力评测。

🔬

PromptFoo

prompt 级别的 A/B 测试与回归测试工具。轻量，易接入 CI，适合快速迭代 prompt 时的对比评测。

🌐

WebArena / AgentBench

学术基准测试集，提供标准化的 Agent 任务（网页操控、代码、数据库等）。适合与公开 SOTA 横向对比。

🏗️

自建 + pytest

对于强定制需求，pytest + mock 工具 + 自定义评分函数往往是最灵活的选择，且与 CI 天然集成。

常见陷阱

五个最常见的评测陷阱

避坑指南
🎭

陷阱①：只测 Happy Path

测试集全是"完美输入"，缺乏边界和对抗用例。结果：线上遇到稍微奇怪的输入就崩。

📈

陷阱②：指标膨胀不收敛

追踪 20+ 个指标，没有主次。结果：每次迭代都有几个指标上升几个下降，无法判断是否进步。

🔁

陷阱③：测试集污染

用 LLM 生成的测试用例直接用于评测同一 LLM，形成自我验证闭环。必须加入人工审核。

📸

陷阱④：快照式评测

只在发布前评测一次，平时改 prompt / 换模型不跑评测。结果：退步无人发现，积累到严重才暴露。

🏆

陷阱⑤：Goodhart's Law

把评测指标当优化目标（如专门训练让 LLM-judge 打高分），导致指标好看但实际能力不升甚至下降。

🌍

陷阱⑥：忽视分布偏移

测试集是 6 个月前建的，但用户行为和任务分布已经变了。定期用生产流量补充测试用例。

当一个指标变成目标，
它就不再是一个好指标了。
— Goodhart's Law，评测设计者最需要牢记的警告
