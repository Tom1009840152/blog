LLM × Recommender Systems

大模型与推荐系统：
LLM + RS 与 LLM as RS

大模型究竟是作为语义增强模块嵌入现有推荐系统，还是直接承担推荐建模与结果生成？本文从传统召回排序、语义 ID、生成式推荐与推荐 Agent 出发，分析两条技术路线的演进与汇合。

2026-08-22 专题 · 推荐系统 阅读约 18 分钟 LLM · 推荐系统 · 生成式推荐

LLM + RS 与 LLM as RS，可以概括大模型进入推荐系统的两条主要路线。但二者更适合作为工程视角下的技术框架，而非相互排斥的严格学术分类。

前者保留推荐系统的骨架，让大模型负责理解、补全或解释；后者把推荐改写成语言建模或序列生成问题，让模型直接预测“下一个物品”甚至整张推荐列表。真正前沿的系统，正在同时吸收两者：既需要协同过滤的行为信号，也需要大模型的世界知识与推理能力。

LLM + RS 研究如何利用大模型增强现有推荐系统。
LLM as RS 则研究如何将推荐过程直接建模为生成任务。
ROUTE 01

LLM + RS

传统推荐系统仍然负责大规模召回、排序和在线学习；LLM 作为特征工程师、教师模型、重排器、解释器或交互层接入。

ROUTE 02

LLM as RS

把用户历史、上下文和物品表示成 token 序列，由语言模型或生成式 Transformer 直接输出物品、物品 ID 或推荐列表。

01 · The real problem

在引入 LLM 之前：推荐并非普通问答

推荐系统表面上是在回答“用户会喜欢什么”，底层却是一个高基数、强反馈、持续变化的决策问题。它和聊天模型至少有四个结构性差异：

  • 输出空间是封闭目录。推荐结果必须是库存里真实存在、当前可展示的物品，而不是一句听起来合理的话。
  • 协同信号往往比文本更诚实。用户说“想看严肃电影”，晚上却连续点开轻喜剧；点击、停留、跳过和复购共同构成真实偏好。
  • 时效与反馈回路极强。新品、热点、库存和兴趣都在变化，模型还会影响自己随后看到的训练数据。
  • 规模与时延苛刻。候选可能以千万乃至十亿计，线上链路却常以几十毫秒衡量。

因此，大模型能读懂“雨天、带孩子、预算 300 元”背后的复合意图，却不天然知道某个用户刚刚跳过了哪条视频，也不天然保证输出一定命中当前目录。语义理解和协同学习，是两类不同的能力。

02 · LLM + RS

路线一：保留推荐系统，让 LLM 增强每一层

这是今天最容易产生业务价值的路线。2024 年的一项综述把它进一步归纳为知识增强、交互增强和模型增强：核心思想都是尽量把昂贵的 LLM 推理移出高频在线链路，或只放在候选已经很小的环节。相关综述：Large Language Model Enhanced Recommender Systems

知识 / 特征
从标题、详情、评论、图片中抽取主题、风格、场景与人群标签；生成统一的物品描述与向量，改善内容稀疏和新品冷启动。
用户理解
把长行为序列压缩为可更新的兴趣摘要，区分长期偏好、短期意图和负反馈；将自然语言需求拆成预算、时间、地点等硬约束。
数据增强
生成查询改写、弱标签、难负样本和解释性属性。LLM 更像离线教师，产物进入小模型训练，而不是每次请求都调用大模型。
重排 / 约束
在传统系统召回的几十或几百个候选上做语义重排，处理“适合雨天、不要太吵、可带儿童”等组合条件。
交互 / 解释
针对缺失条件发起澄清、解释推荐理由并支持对话式调整；相关解释必须受到真实特征和排序证据约束，避免生成缺乏依据的理由。

为什么这一路线更早获得应用？

这一路线无需重构已经稳定运行的召回—粗排—精排体系。工程团队可以从低风险环节开始：先离线生成标签，再让 LLM 处理较小的候选集，最后通过蒸馏将能力迁移至轻量模型。其系统边界明确，也更容易设计回退机制。

一个重要反例 A-LLMRec 的研究发现，只依赖语言语义的模型在暖启动场景可能输给简单协同过滤；它因此把预训练 CF 模型中的用户/物品嵌入对齐给 LLM。这个结果提醒我们：大模型知识不能自动替代“谁和谁一起点过”的协同知识。 查看论文
03 · LLM as RS

路线二：让模型直接“生成”推荐结果

这条路线的初级形态，是将用户历史写入提示词，由通用 LLM 列出电影或商品。更具代表性的技术方向则是：将推荐对象编码为模型可以生成、同时能够映射回真实目录的 token。

形态 A：自然语言直接推荐

模型根据对话、用户画像和少量示例，直接输出名称或候选序号。优点是零样本能力强、能解释复杂约束；缺点是容易推荐不存在或已下架的物品，热门偏置明显，也难吸收海量隐式反馈。更稳妥的做法，是让它只在给定候选中选择，或通过检索工具查询目录。

形态 B：推荐任务统一成语言任务

P5 把点击预测、序列推荐、评分预测、解释生成等任务统一成 text-to-text：所有用户、物品、交互和元数据都转成语言序列，并用同一个语言建模目标训练。这证明了“一套模型、多种推荐任务”的可行性。P5 论文

形态 C：生成语义 ID

直接生成商品名太自由，直接生成随机物品 ID 又没有语义。TIGER 的做法是先把物品内容量化成一串有层级语义的代码，再训练序列模型根据用户历史生成下一个物品的 Semantic ID。相似物品共享部分代码，新物品即使缺少交互，也可能凭语义落到正确区域。TIGER / Generative Retrieval 论文

形态 D：端到端生成一张列表

2025 年的 OneRec 进一步尝试用单一生成模型统一召回与排序：编码用户历史后，按 session 生成一组视频，并引入 MoE 扩展容量、用偏好对齐优化列表质量。论文报告其在快手主场景上线后带来观看时长提升。它很重要，因为生成式推荐不再只是学术数据集上的 next-item prediction，而开始触及工业级级联系统的核心链路。OneRec 论文

术语边界 并非所有“生成式推荐”都是自然语言大模型。HSTU 将推荐建模为序列转导，并把架构扩展到工业规模，它借鉴了 Transformer 与生成建模思想，但输入输出主要是行为与物品序列，不等于拿一个聊天 LLM 直接推荐。把二者区分开，才能避免把“LLM as RS”无限泛化。HSTU 论文
04 · Compare

两条路线的适用边界

维度LLM + RSLLM as RS
系统核心召回、排序仍由传统推荐模型承担模型直接预测物品 token、ID 或列表
协同信号天然继承现有行为特征与在线学习需要专门把协同嵌入、行为序列注入模型
冷启动可用 LLM/多模态特征补充语义语义 ID 与预训练知识有更大潜力
目录约束候选来自真实索引，结果更可控必须约束解码或回查索引，防止无效物品
时延成本可离线处理，或只在小候选集调用自回归解码与大模型服务成本更高
可解释交互容易接入对话与解释模块语言交互与推荐目标可在同一模型统一
适合场景大规模成熟业务、渐进升级研究型重构、高价值决策、生成式召回

工程实践通常不要求在两条路线之间进行排他性选择。大规模目录可以先由高吞吐召回系统压缩，再由生成模型完成语义理解、生成式召回或精细重排；也可以利用 LLM 离线生成知识，并将结果蒸馏至线上模型。两条路线最终会在混合架构中汇合。

这个架构把大模型放在它擅长的地方：理解非结构化信息、组合约束、补充知识和进行交互；把传统推荐放在它擅长的地方：处理大规模稀疏反馈、低延迟检索、在线更新与精确约束。

“周末带六岁孩子出去玩，上海下雨，预算 300 元以内，不想去太吵的地方。”

LLM + RS

LLM 抽取地点、天气、亲子、预算、噪声敏感等约束；地图/本地生活召回返回真实营业场所；排序模型结合距离、历史点击和实时热度；LLM 对前 30 个候选重排并解释理由。

LLM as RS

模型将对话与历史编码后生成若干场所的语义 ID 或工具调用；系统将 ID 映射回目录、校验营业状态和价格，再生成组合方案。若直接生成店名而不查目录，幻觉风险会很高。

06 · Frontier

截至 2026 年，值得关注的五个前沿方向

SEMANTIC ID

物品 ID 正在变成“可生成的语言”

语义量化把开放语义与封闭目录连接起来，是生成式召回能否规模化的关键基础设施。

UNIFIED GENERATION

召回与排序开始统一优化

从 next-item 到 session/list generation，目标不再只是单个物品相关性，而是整张列表的连贯、多样与长期收益。

MULTIMODAL

图片、视频、文本共同描述偏好

MLLM 可把视觉内容转成可检索语义，也能从行为与内容联合推断用户偏好，尤其适合服饰、短视频和本地生活。

AGENTIC REC

推荐从单次输出走向决策辅助

Agent 通过记忆、规划与工具调用追问需求、查库存、比较约束并执行下一步，但也带来更难的安全和长期评估问题。

TEACHER → STUDENT

大模型离线指导，轻量模型在线执行

生成特征、标签和偏好解释，再蒸馏到低成本模型，往往比全量在线调用更符合工业性价比。

ALIGNMENT

从点击率转向列表与长期价值

偏好优化、奖励模型和序列级目标开始进入推荐，但奖励偏差、反馈污染与探索成本仍是硬问题。

推荐 Agent 被视为下一阶段的重要产品与研究方向。相关研究已从单次对话扩展至记忆、规划、工具使用和多模态感知；与此同时，安全、效率、可控性和持续个性化仍是尚未解决的问题。Agentic Recommender Systems 观点论文

07 · Evaluation

别只看“回答像不像”：怎么评估？

推荐准确性

Recall@K、NDCG@K、Hit Rate、MRR；生成式模型还要测合法物品率与去重率。

体验与约束

多样性、新颖性、覆盖率、约束满足率、解释忠实度、对话完成率。

线上与系统

CTR/CVR、停留、留存、负反馈，以及 P95 延迟、token 成本、吞吐和降级率。

离线相关性仅是基础评估条件。LLM 可能生成更具说服力的理由，却未必提高真实满意度；也可能提高短期点击，同时降低多样性并加剧流行偏置。因此仍需通过受控线上实验，持续观察长期留存与负反馈。

08 · Pitfalls

五个最常见的误区

01

让模型自由生成商品名。没有受约束解码、候选选择或目录回查，就无法保证结果真实、可售、合规。

02

把完整历史塞进提示词。长上下文既贵又噪，应该做时间衰减、兴趣分层与摘要，并保留关键负反馈。

03

认为文本语义足以替代协同过滤。语义信息描述物品的内容与属性，行为网络则反映真实选择关系，二者承担不同且互补的作用。

04

把解释当成因果证据。流畅理由可能只是合理化；解释应引用真实属性、约束命中和可追溯的排序信号。

05

只在静态公开集上追分。提示词污染、热门记忆和数据泄漏都可能抬高结果，线上目录变化与反馈回路才是更难的问题。

09 · Roadmap

面向工程落地的演进路线

Step 0 · 先把传统基线做好

明确候选规模、延迟预算、业务目标和现有 Recall/NDCG；没有基线，就无法判断大模型是否真的创造增量。

Step 1 · 从离线语义增强开始

生成物品标签、评论摘要、查询改写和用户兴趣摘要，写入特征库；成本可控，也最容易做消融实验。

Step 2 · 在小候选集上做在线重排

只让 LLM 处理 Top 20–100 个候选，并用结构化输出、目录 ID、超时降级和缓存约束它。

Step 3 · 影子测试生成式召回

构建 Semantic ID 与受约束解码，先与传统召回并行，观察覆盖、冷启动、延迟和长尾收益，再逐步放量。

Step 4 · 把 Agent 留给高价值决策

旅行、教育、汽车、B2B 采购等复杂场景更适合多轮澄清、工具调用和方案比较；低价值高频 feed 未必值得完整 Agent 链路。

在可预见阶段，混合架构比“LLM 完全取代推荐系统”更具可行性：协同模型继续承担规模化检索、时效建模与反馈学习，大模型则补充语义理解、推理和交互能力。

因此可以得出一个相对稳健的判断：LLM + RS 是当前工程应用的主要路线，LLM as RS 代表架构演进的重要前沿，而两者正在 Semantic ID、生成式召回与推荐 Agent 等方向中逐步汇合。
