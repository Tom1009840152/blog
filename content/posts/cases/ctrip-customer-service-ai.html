Real-world AI Transformation

携程客服 AI 转型：
传统机器人与 LLM 的协同

当咨询规模、推理成本与知识债务同时成为约束，客服系统的升级重点便不再是“是否使用大模型”，而是如何让大模型参与知识治理，并与传统机器人形成分层协作。

2026-08-22 真实案例 · 第一版 阅读约 12 分钟 客服 AI · LLM · 知识治理

大模型进入客服场景后，一个常见判断是：传统机器人将被自然语言能力更强的 LLM 直接替代。携程客服 AI 转型案例呈现了另一种更符合大规模业务现实的路径——保留传统系统的低成本与高吞吐优势，同时利用 LLM 改造其长期积累的知识生产、清理、归并和标注流程。

案例说明 本文为第一版方法复盘，重点讨论业务约束、系统分层与知识治理机制，不涉及未经确认的内部指标。机票与火车票的业务划分依据当前案例材料表述，后续可结合更具体的流程、数据和组织分工继续修订。
这不是一次“用 LLM 替换旧机器人”的改造，而是一次“用 LLM 治理旧机器人”的系统升级。
01 · Traditional architecture

传统客服机器人：规则树与 Embedding 的组合

在大模型出现之前，成熟客服机器人通常依赖两类能力协同工作：一类是规则树，负责业务流程、条件判断和确定性回复；另一类是语义向量检索，负责将表达各异的用户问题匹配到标准问题或知识节点。

Traditional service pipeline
用户问题口语、错别字、多种表达
意图识别分类模型 / Embedding
规则树路由业务条件与流程节点
标准答案QA / 模板 / 接口结果
当语义匹配置信度不足、规则条件冲突或流程无法覆盖时，请求会转入人工客服。

规则树适合回答确定性强的问题，例如退改条件、出票状态和证件要求；Embedding 模型则解决“同一个问题存在多种问法”的问题。例如，“火车晚点能退吗”“列车延误怎么退款”“没按时发车是否能退票”都可能映射到同一个标准问题。

这类架构具有三个显著优势：推理成本低、响应速度快、输出范围可控。因此，即使 LLM 已经具备更强的语言理解能力，传统机器人在超大规模客服链路中仍具有明确价值。

02 · Scale and cost

核心矛盾：咨询规模很大，全量使用 LLM 成本过高

火车票客服每天需要处理大量用户咨询，购票旺季的流量压力更为明显。若所有请求都通过大模型完成意图识别、知识检索、推理和答案生成，token 成本、响应延迟、并发容量和输出稳定性都会成为新的系统约束。

另一方面，不同业务场景对智能化投入的承受能力并不相同。机票业务具有更高的客单价和服务价值，问题通常也更复杂，对多轮理解、组合条件判断和个性化解释的需求更高；火车票业务的直接收益有限，但咨询量巨大，更适合由低成本、高吞吐的传统系统承担主要流量。

HIGH-VALUE / COMPLEX

机票等高价值场景

允许承担更高推理成本。LLM 可用于复杂意图理解、多轮澄清、方案比较、异常处理和答案生成，必要时结合业务工具完成查询。

HIGH-VOLUME / LOW-MARGIN

火车票等高流量场景

继续以规则树和 Embedding 模型处理高频标准问题，LLM 更多承担离线治理、低置信度兜底和辅助质检，而不是全量在线推理。

维度传统机器人LLM
单位成本低，适合大规模重复请求较高，随上下文与输出长度增长
响应延迟稳定，链路较短受模型规模、并发和工具调用影响
语言理解依赖训练数据和人工规则覆盖擅长复杂表达、上下文和组合意图
答案控制标准化程度高，边界明确需要检索、结构化输出和安全校验
主要价值处理高频、确定、低价值问题处理复杂、高价值、低覆盖问题

因此，合理的目标并非追求 LLM 调用比例最大化，而是按照问题价值、复杂度和风险配置不同的计算成本。

03 · Knowledge debt

真正的瓶颈：规则树不断累积，知识开始失去治理

传统机器人的主要问题并不只是语言理解能力有限。随着业务持续变化，规则树和 QA 知识库会不断增长，并逐渐形成类似遗留代码的“知识债务”。

01

规则只增不减。业务变化通常会触发新增规则，但很少有人能够确认旧规则是否仍在使用、是否已经过期。

02

知识所有权丢失。原始维护人员流动后，规则的业务背景、适用边界和设计原因难以追溯，清理风险随之上升。

03

重复与冲突增加。同类问题可能被不同团队写成多个 QA 节点；新旧答案并存，导致检索结果相互竞争。

04

系统性性能下降。知识节点越多并不意味着覆盖越好。失效、重叠和边界模糊的知识会降低意图分类与向量召回的准确率。

此时继续增加标注人员或扩展规则树，只会加快知识膨胀。问题已经从“答案是否足够多”转变为“知识是否标准、有效、可追踪和可维护”。

04 · LLM as knowledge governor

解法：将 LLM 放在知识治理层

LLM 的主要价值并非替代每一次在线回答，而是将分散、非结构化且缺乏维护的业务知识，整理为可复用、可比较、可审计的标准知识集合。围绕这一目标，可以形成四个连续步骤。

知识抽取：构造标准知识集合

从历史 QA、规则文档、客服话术、工单和真实对话中抽取标准问题、适用条件、答案、例外情况、来源与有效期。LLM 负责理解和结构化，业务人员负责确认高风险知识。

OUTPUT · CANONICAL KNOWLEDGE SET

存量清理：识别过时、重复和冲突知识

将旧 QA 与标准知识集合进行语义对齐，输出保留、合并、改写、下线或人工复核建议。系统不直接删除知识，而是形成带证据的治理队列，并保留版本和回滚能力。

OUTPUT · CLEANUP QUEUE

增量准入：判断新问题是否进入知识树

对新增问题先执行相似知识检索，再由 LLM 判断其属于已有问题的新表达、已有节点的补充条件，还是确有必要创建的新知识节点，从源头控制知识树继续膨胀。

OUTPUT · MERGE / EXTEND / CREATE

标注与抽检：提高 Embedding 模型的训练质量

用户原始问题需要标注到对应的标准问题，才能训练更准确的意图与 Embedding 模型。LLM 可以生成候选标签、解释匹配依据并辅助抽检；低置信度、冲突或高风险样本继续由人工确认。

OUTPUT · WEAK LABELS + QA REVIEW

标准知识不应只有“问题与答案”

如果标准知识集合仍然只是两列 QA，后续治理能力依旧有限。更合理的知识单元应当具备清晰的业务边界与生命周期字段。

05 · System role shift

关键变化：LLM 从“回答者”转向“知识治理者”

直接替代思路

每个请求都调用 LLM，由模型完成理解、检索、推理和生成。能力上限较高，但在线成本和稳定性压力集中。

→
协同治理思路

LLM 负责离线知识抽取、清理、归并与标注；传统模型继续处理主要流量，仅将复杂或高价值问题交给 LLM。

这种角色变化带来一个重要结果：大模型能力可以通过标准知识、训练数据和模型蒸馏被复用，而不需要在每一次用户请求中重复支付完整推理成本。

06 · Evaluation

评估重点：不仅关注回复准确率

知识质量

重复率、过期知识召回率、冲突发现率、合并准确率、知识覆盖率。

模型效果

意图分类准确率、Top-K 召回率、低置信度比例、标注一致性。

服务效果

机器人解决率、转人工率、重复咨询率、平均处理时长与用户满意度。

治理效率

知识审核耗时、单人处理量、自动建议采纳率、待清理知识积压。

系统成本

单次咨询成本、LLM 调用率、平均 token、P95 延迟与峰值容量。

安全与稳定

错误下线率、知识回滚率、无依据回答率、高风险问题拦截率。

LLM 建议不能直接等同于知识事实

知识清理和节点合并具有不可逆风险。系统应保存原始来源、模型判断、置信度和审核记录；涉及退改规则、费用、证件与合规的知识，需要设置更高审核等级，并支持版本回滚。

07 · Implementation roadmap

一条可执行的落地路线

阶段一 · 盘点存量知识

统一收集 QA、规则、工单、客服话术和命中日志，建立来源、负责人、更新时间与使用频次视图。

阶段二 · 离线构建标准知识

选择高频但风险较低的业务域，验证抽取、聚类、冲突发现和人工审核流程，不直接影响线上回答。

阶段三 · 清理知识并改进训练数据

以标准集合清理旧 QA，利用 LLM 辅助标注用户问法，重新训练意图与 Embedding 模型，开展离线回放。

阶段四 · 建立增量治理闭环

所有新增问题进入相似检索、合并判断和分级审核流程，防止知识树再次无序增长。

阶段五 · 选择性接入在线 LLM

在高价值、复杂或低置信度场景逐步启用 LLM，通过路由、预算、超时与降级策略控制在线成本。

携程客服 AI 转型案例的核心，不是模型能力竞赛，而是对计算成本、业务价值和知识生命周期进行重新分配。

传统机器人仍然适合承担高频、确定、低成本的服务请求；LLM 则被配置到复杂问题和知识治理环节。最终形成的并非两套相互替代的系统，而是一套由价值分层驱动、由标准知识连接的混合客服架构。
