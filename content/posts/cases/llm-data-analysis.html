REAL-WORLD CASE · DATA INTELLIGENCE

LLM 与数据分析：
从写 SQL 到可信问数

大模型可以缩短找表、写 SQL 和解释结果的时间，却无法自动消除历史数据债务。酒店集团的实践说明，智能问数的真正基础不是更强的模型，而是可检索的元数据、统一的业务口径和受治理的执行链路。

导言 · Introduction

传统数据分析的主要产物看似是一段 SQL 或一张报表，实际工作却包含需求澄清、指标定义、数据发现、字段理解、查询编写、结果验证与多轮沟通。LLM 能够加速其中的语言和代码环节，但如果表找不到、字段没有定义、业务周期没有统一，模型只会更快地产生一个语法正确却业务错误的答案。

案例口径 · Scope 本文依据当前案例材料复盘华住与携程的数据分析实践，并结合公开资料补充技术边界。公开材料能够确认两家公司已在受控环境中使用大模型基础设施，但没有完整披露 Text-to-SQL 的覆盖范围、准确率和节省工时。因此，文中不填写未经确认的内部指标；华住“正在尝试”、携程“2025 年已用于内部 SQL 辅助”的表述，暂按案例材料记录，后续可随更多流程和数据继续修订。
LLM 可以减少数据分析流程中的机械劳动，但不能替代数据语义。企业真正需要建设的不是一个“会写 SQL 的聊天框”，而是一套能够理解指标、查找证据、约束执行并解释结果的可信问数系统。
01 · TRADITIONAL WORKFLOW

传统数据分析流程：从业务问题到可用数据

以酒店集团为例，一次分析通常从业务或产品团队提出需求开始。需求可能是“最近两周华东区域的入住率为什么下降”，也可能只是“拉一份活动酒店的经营数据”。数据分析师首先需要判断问题是否清晰、指标是否已有定义，以及完成分析需要哪些数据。

理解需求与确定指标

明确分析对象、时间范围、对比基准、筛选条件、粒度和交付形式。模糊的“收入”“订单”“入住率”必须拆成可计算口径。

寻找数据表与字段

若所需数据属于常用主题，分析师可以直接选择熟悉的表；若涉及陌生业务，则需要与数仓团队沟通，确认来源表、汇总表、关联键和更新周期。

编写 SQL 并提取样本

先查询少量数据，检查字段取值、空值、重复、时间跨度与数量级，再判断表和口径是否符合需求。

组合分析数据集

根据需求筛选字段，完成多表关联、指标计算、分组聚合和异常处理，构造最终数据集或报表。

解释结果并继续迭代

业务查看第一版结果后，常会补充条件、改变统计范围或提出新的拆分方式，分析师随后重新查表、改 SQL、取数和解释。

结论与下一轮
SQL 只是流程中间的一步。其上游依赖需求和业务语义，下游还需要数据验证、解释与决策沟通。
02 · BOTTLENECKS

三个主要难点：找不到、说不清、反复改

01 · DISCOVERY

数据分散，找表本身就很耗时

订单、房态、会员、价格、渠道、活动和酒店主数据分布在不同主题域。表名不一定表达业务含义，同一概念还可能存在明细表、快照表、汇总表和历史版本。

02 · METADATA

元数据存在，但没有业务解释

字段类型和注释不足以说明数据如何产生。某个收入字段是否含税、是否扣除退款、按预订日还是入住日归属，往往只存在于旧 SQL、报表逻辑或个人经验中。

03 · COMMUNICATION

业务需求需要通过数据逐步成形

业务不一定预先知道需要哪些字段和拆分维度。第一版数据常常只是问题探索的开始，查看分布后才会产生更具体的需求，形成反复取数与沟通。

这些问题会把数据分析师变成组织内部的“数据翻译器”：既要理解业务问题，又要记住表与字段，还要解释历史口径。分析能力被大量消耗在搜索、确认和重复改写上，真正用于提出假设、判断因果与解释业务的时间反而被压缩。

业务先提一个问题目标和数据形态尚不完整
→
分析师先拉一版数据通过真实分布澄清问题
↺
业务继续补充需求增加维度、口径或筛选条件
多轮沟通并非需求方或分析师能力不足，而是分析问题具有探索性。风险在于每一轮探索都必须重新经过人工找表、写 SQL 和解释字段，导致反馈周期过长。

携程技术较早公开过其数据血缘建设实践：企业数据会经过 Hive、Spark、Presto、DataX 等多种引擎和工具流转，需要建立表级与字段级血缘，才能支持溯源、影响分析、生命周期和安全管控。这个案例说明，数据发现和元数据治理在大模型出现之前已经是独立且长期的工程问题。参见《携程数据血缘构建及应用》。

03 · LLM INTERVENTION

引入 LLM：不是只把自然语言翻译成 SQL

最直观的应用是 Text-to-SQL：业务用自然语言提问，模型生成查询语句。但企业分析系统需要处理的远不止语法转换。一个有价值的 LLM 数据助手，应当覆盖需求澄清、数据发现、字段解释、SQL 生成、执行校验和结果解读。

01 · CLARIFY

需求澄清

识别问题中的指标、维度、时间、粒度和对比关系；遇到“收入”“本周”“有效订单”等歧义时，先给出候选口径并请求确认。

02 · DISCOVER

智能找表

从数据目录、字段注释、血缘、历史 SQL、报表和文档中检索候选表，解释推荐依据，并展示负责人、更新频率与上下游关系。

03 · GENERATE

SQL 生成与修改

根据受控上下文生成 SQL，解释关联键、过滤条件与指标公式；分析师可以继续用自然语言要求增加字段、改变粒度或优化性能。

04 · VALIDATE

查询验证

进行语法检查、权限检查、扫描成本预估、危险操作拦截，并通过小样本执行、结果约束和历史查询对比发现异常。

05 · EXPLAIN

结果解释

总结趋势、异常和维度贡献，同时保留 SQL、口径、来源表和运行时间，使结论能够追溯到计算证据。

06 · ITERATE

对话式迭代

保存当前分析上下文，支持“只看华东”“按品牌拆分”“排除新开店”等连续修改，缩短业务与数据之间的反馈回路。

2025 年的 LinkedIn 企业 Text-to-SQL 研究采用了类似思路：先把数据库元数据、历史查询、Wiki 和代码组织成知识图谱，再由 Agent 检索上下文、生成 SQL 并修正语法或幻觉。其内部评测中，专家认为正确或接近正确的回答约占 53%。这不是一个可以直接横向比较的行业准确率，却说明即使拥有企业知识图谱和自动修正，生产级问数仍远未达到完全自治。参见Text-to-SQL for Enterprise Data Analytics。

04 · COMPANY PRACTICE

华住与携程：从探索到内部辅助

EXPLORATION · 案例材料

华住集团：尝试让 LLM 查表、写 SQL 和回答业务问题

按照当前案例材料，华住的探索方向是把 LLM 接入数据分析流程，让模型根据业务问题查找相关表、生成 SQL，并基于查询结果回答问题。目标是降低业务自助取数门槛，同时减少数据分析师在重复找表和改写查询上的投入。

华住的《2025 可持续发展报告》公开说明，其 AI 模型运行在自建 VPC 环境并集成多家国产大模型，以确保数据在受控环境中处理。报告能够支持其内部大模型基础设施与安全方向，但没有披露智能问数的具体范围和效果。

INTERNAL ASSISTANT · 2025 案例材料

携程集团：内部部署 LLM 辅助 SQL 编写

按照当前案例材料，携程在 2025 年已经使用内部部署的大模型协助分析师编写 SQL，主要价值是缩短查询草稿、字段组合和反复修改的时间，让分析师把更多精力放在需求判断与结果解释上。

携程研发总监在 2025 年公开演讲中介绍，内部 AI 网关同时接入外部商业模型与内部自研模型，并运行在企业内部 Kubernetes 集群；这为敏感数据场景中的模型调用和统一治理提供了基础。该公开演讲没有披露 SQL 助手的覆盖率或节省工时，本文不据此推算。参见携程 AI 网关实践公开演讲整理。

这两条路径的共同点不是让业务直接绕过数据团队，而是先把 LLM 配置为分析助手：帮助理解需求、发现数据和生成查询，再由分析师确认口径与结果。节省的是可重复的检索和编码时间，保留的是业务判断、数据责任和最终解释权。

05 · UNSOLVED DEBT

仍未解决的问题：历史数据债务不会被模型自动消除

LLM 能够读取元数据，却不能补回从未记录的业务知识。企业数仓中的多数困难并不是 SQL 写法，而是同一个指标存在多种口径、历史逻辑缺少负责人、字段与报表长期漂移。模型会把这些不确定性吸收进回答，甚至用流畅语言掩盖冲突。

SQL 可执行 ≠ 数据正确 ≠ 业务结论可信
语法正确只说明数据库可以运行查询。表是否选对、关联是否重复、时间是否按业务周期截取、指标是否符合组织定义，决定了结果能否用于经营判断。
TABLE DEBT
表的数量与历史版本持续增加同一主题存在明细、快照、宽表、临时表和废弃表。没有生命周期和使用热度时，LLM 同样难以判断哪个表才是当前可信来源。
METADATA DEBT
字段注释缺少计算和业务含义名称为 revenue 的字段可能是含税收入、净收入或确认收入；类型信息无法表达退款、取消和跨日归属规则。
CALENDAR DEBT
酒店业务的时间不是自然日历的简单映射营业日可能跨越自然日；“周”可能遵循企业经营周期；预订日、入住日、离店日和收入确认日会产生不同分析结果。
METRIC DEBT
指标定义散落在报表和个人 SQL 中入住率、平均房价、RevPAR、取消率等指标依赖过滤条件、可售房口径、分母选择和异常订单处理。
OWNERSHIP DEBT
旧逻辑失去维护者分析师能够找到一段历史 SQL，却无法确认它为何这样计算、是否仍然有效，以及变更后会影响哪些下游报表。

Spider 2.0 将企业级 Text-to-SQL 任务扩展到真实数据工作流：数据库常包含超过 1,000 个字段，任务还需要理解元数据、方言文档和项目代码，并可能生成超过 100 行的多段 SQL。论文中的代码 Agent 在该评测上只解决了 17.0% 的任务，远低于其在传统 Spider 1.0 上的结果。这个差距表明，真实企业环境的困难主要来自复杂上下文和业务工程，而不仅是模型是否会写 SELECT。参见Spider 2.0。

06 · SEMANTIC LAYER

关键解法：为 LLM 建立可治理的语义层

如果模型直接面对数千张原始表，只靠向量检索选择 schema，生成结果很容易随提示和候选表变化。更稳定的做法是在数据库与 LLM 之间建立语义层，把业务术语、指标公式、允许关联、时间日历、权限和负责人集中管理。

GOVERNED METRIC · HOTEL_OCCUPANCY_RATE
business_name酒店入住率
formula已售房晚 / 可售房晚
grainhotel_id × business_date
calendar酒店营业日，不直接等同自然日
filters取消单、测试单与维修房规则
dimensions品牌、区域、城市、渠道
source受治理事实表与版本
owner收益管理 / 数据产品负责人
lineage上游字段、任务与下游报表
validity生效时间、变更记录与状态

语义层不是专门为 LLM 创建的新文档，而是企业原本就需要的数据产品。它让分析师、报表、API 和 AI Agent 使用同一套指标定义。Thoughtworks 在 2025 年将无人监督 Text-to-SQL 调整为“Hold”，建议通过受治理的数据抽象或语义层限制直接数据库访问；其理由正是模型可能因为 schema 和领域理解不足而生成错误查询。参见Technology Radar：Text to SQL。

不要让 LLM 直接拥有不受限制的生产库权限

生产系统至少需要只读账号、行列级权限、敏感字段脱敏、查询超时、扫描量限制、SQL AST 检查、危险函数拦截、结果行数限制和完整审计。高风险查询应先展示 SQL、口径与预计成本，由分析师确认后执行。

07 · EVALUATION

如何评估：不能只统计 SQL 是否执行成功

可信问数需要端到端评测。评测问题应来自真实业务请求，保存标准口径、允许表、参考 SQL、预期结果约束和必要澄清项，并按照简单取数、复杂关联、业务日历、长尾指标和高风险数据分层。

数据发现

正确表 Top-K 召回率、字段召回率、血缘引用正确率与找表耗时。

语义理解

指标识别、时间口径、粒度、过滤条件和歧义澄清的准确率。

SQL 质量

语法执行率、结果一致率、关联正确率、扫描成本与性能。

答案可信度

结论是否由查询结果支持，是否附带口径、来源、SQL 和时间戳。

安全治理

越权查询拦截率、敏感字段泄露率、危险 SQL 率和审计完整度。

业务效率

首次可用结果时间、往返轮次、分析师修改量、问题解决率和节省工时。

08 · IMPLEMENTATION

落地路线：先做分析师助手，再做业务自助问数

阶段一 · 选择一个数据治理较好的主题域

从酒店经营、渠道或会员等单一领域开始，限定可信表、指标和用户群，不直接接入全集团全部数据。

阶段二 · 上线分析师 Copilot

先提供找表、字段解释、历史 SQL 检索和查询草稿。SQL 由分析师审核执行，收集修改前后的差异作为评测与改进数据。

阶段三 · 补齐语义与数据债务

根据失败样本补充指标公式、业务日历、表粒度、关联规则、负责人和血缘；让每次模型失败推动数据资产变得更清晰。

阶段四 · 建立受控执行链路

引入只读沙箱、权限、扫描成本、AST 校验、结果约束与审计。先允许低风险聚合查询自动执行，高风险请求继续人工确认。

阶段五 · 向业务开放有限自助问数

只开放已治理的指标与维度，答案必须展示口径和来源。遇到歧义、异常或未治理领域时转回分析师，而不是由模型猜测。

阶段六 · 建立反馈与版本闭环

记录问题、检索上下文、生成 SQL、修改、执行结果与用户反馈；模型、语义层和评测集分别版本化，避免改动后无法追责。

这一顺序保留了分析师作为质量控制点，也能较快产生价值。模型最先替代的是复制表名、查字段、改 SQL 和整理说明等重复步骤；随着语义资产和评测体系成熟，系统才逐步承担低风险的自动取数。若一开始就让业务自然语言直接驱动生产查询，错误会在最难审计的位置发生。
